2.1 Request-Response Lifecycle Flow

  1. Ingress: Incoming requests hit the Express gateway. CORS middleware validates the Origin header against the allowed client URL (http://localhost:5173).
  2. Payload Inspection: Express JSON body-parser parses incoming payloads with a safety ceiling of 6MB (accommodating base64 profile pictures safely while mitigating memory DoS).
  3. Cryptographic Authentication Guard (protect): The gateway inspects the Authorization: Bearer <token> header. The token is cryptographically verified against JWT_SECRET. The user record is hydrated from MongoDB (excluding password) and attached to req.user.
  4. Declarative Role Authorization Guard (authorize): Route-level guards check req.user.role. If the role is not explicitly whitelisted, the request is terminated immediately with HTTP 403 Forbidden.
  5. Controller Execution: The business controller executes domain logic, queries Mongoose schemas, and issues deterministic JSON responses.
  6. Global Error Handling: Unhandled exceptions, MongoDB cast errors, and validation errors are intercepted by a centralized error-handling middleware that returns sanitized diagnostic messages.

3. Database Architecture, Schema Design, & Relational Invariants

The database engine is MongoDB (NoSQL Document Store) interfaced via Mongoose 8.5 ODM. Educational software demands relational guarantees; SchoolSync solves this through Single-Table Discriminators and Compound Unique Indexing.

3.1 The User Discriminator Entity Pattern

Rather than splitting users into three disconnected tables (which forces complex joins or multiple authentication paths), all system identities reside in the User collection. The role field acts as a schema discriminator:

Field Name BSON Type Constraints Domain Description & Architectural Function
_id ObjectId Primary Key Immutable 12-byte BSON identifier assigned by MongoDB.
name String Required, Trim Legal full name of student, faculty member, or system administrator.
email String Required, Unique, Lower Unique login identifier; indexed uniquely to guarantee zero duplicate accounts.
password String Required, MinLength 6 Bcrypt-hashed password string. Stripped from all projections via select("-password").
role String Enum, Indexed Discriminator key: admin, teacher, student, guardian.
rollNo String Indexed Student academic roll number (e.g. "4"). Allows direct numeric student login.
class String Indexed Student grade cohort (e.g. "10", "3", "Grade 12"). Sources the discovery engine.
section String Indexed Student section cohort (e.g. "A", "B", "C").
teacherId String Optional Faculty employee identifier code (e.g. "FAC-ENG-001").
monthlySalary Number Default: 0 Base monthly salary for faculty. Strictly protected from student view.
status String Default: "Active" Account operational status ("Active" or "Inactive"). Checked at login.
accessProtocol String System Stamp Audit protocol classification: ADMIN_SECURE_V1, TEACHER_SECURE_V1, STUDENT_SECURE_V1.

3.2 Complete Schema Catalog for Auxiliary Collections

1. Attendance Collection (attendances)

  • student (ObjectId, ref: User, required): The target enrolled student.
  • class (String, required), section (String, required): The target academic cohort.
  • date (String, format "MM/DD/YYYY", required): The roll-call date.
  • period (String, default "Daily (Full Day)"): The lecture hour or daily indicator.
  • status (String, enum: ["present", "absent", "late"], default: "present").
  • markedBy (ObjectId, ref: User): The faculty member who recorded the roll call.
  • Compound Unique Index: { student: 1, date: 1, period: 1 } (unique: true). Guarantees that a student cannot have conflicting roll-call entries for the same date and lecture block.

2. Fee Collection (fees) & Payment Ledger (payments)

  • student (ObjectId, ref: User, required), class (String), section (String).
  • month (String, e.g. "November"), year (String, e.g. "2026").
  • totalAmount (Number, default: 0): Total tuition dues invoiced for the period.
  • paidAmount (Number, default: 0): Cumulative collected fees.
  • settlementStatus (String, enum: ["PENDING", "PARTIAL", "PAID"]): Finite state machine attribute.
  • Compound Unique Index: { student: 1, month: 1, year: 1 } (unique: true). Prevents duplicate billing cycles.
  • Payments Collection: Stores discrete receipts with transactionId, receiptNumber, amount, paymentMethod, and receivedBy clerk reference.

3. Timetable Collection (timetables)

  • class (String), section (String), day (String, e.g. "Monday" to "Saturday"), period (Number, 1 to 8).
  • timeSlot (String, e.g. "09:00 AM - 09:45 AM"), subjectName (String), subjectCode (String).
  • faculty (ObjectId, ref: User), facultyName (String), roomNumber (String).
  • Conflict Prevention Indexes: { class: 1, section: 1, day: 1, period: 1 } (Classroom conflict) and { faculty: 1, day: 1, period: 1 } (Faculty double-booking prevention).

4. Sessional Marks Collection (sessionalmarks)

  • student (ObjectId, ref: User), class (String), section (String).
  • assessmentType (String, e.g. "1st Sessional", "2nd Sessional", "Mid-Term").
  • subject (String), maximumMarks (Number, default: 100), marksObtained (Number).
  • grade (String, computed: A+, A, B, C, F), status (String, "PASS" | "FAIL"), remarks (String).

5. Notices, Materials, Exams, & Audit Collections

  • notices: title, content, category ("General", "Exam", "Holiday", "Fees"), audience ("EVERYONE", "TEACHER", "STUDENT"), publishedBy (ObjectId).
  • materials: title, targetClass, section, category ("STUDY MATERIAL", "PAPER", "HOMEWORK"), subject, link, uploadedBy (ObjectId).
  • exams: examName, targetClass, examDate ("DD/MM/YYYY"), description, createdBy (ObjectId).
  • audit_logs: action (e.g. "FEE_PAYMENT_COLLECTED"), performedBy, targetEntity, details (BSON delta), ipAddress, timestamp.

4. Core Functional Modules & Business Logic Implementation

4.1 The Dynamic Database-Driven Class Discovery Engine

A critical architectural refinement in this ERP was the complete eradication of manual text input boxes for class and section parameters.

Problem Analysis: In early systems, administrators and teachers typed target classes manually (e.g., typing "Grade 10" in one form, "10" in another, or "Class X" in a third). This fractured search queries and permitted selecting non-existent sections, leading to orphaned database records.

Engine Architecture: The backend exposes an optimized aggregation pipeline (GET /api/students/classes-sections) that queries active student documents in MongoDB: 

const getClassesAndSections = async (req, res) => {
  const students = await User.find({
    role: "student",
    class: { $exists: true, $nin: ["", "Unassigned", null] },
  }).select("class section");

  const map = {};
  students.forEach((s) => {
    const cls = String(s.class).trim();
    const sec = s.section ? String(s.section).trim() : "";
    if (!cls) return;
    if (!map[cls]) map[cls] = new Set();
    if (sec) map[cls].add(sec);
  });

  const result = Object.keys(map)
    .sort((a, b) => {
      const numA = parseInt(a.replace(/\D/g, ""), 10);
      const numB = parseInt(b.replace(/\D/g, ""), 10);
      if (!isNaN(numA) && !isNaN(numB) && numA !== numB) return numA - numB;
      return a.localeCompare(b);
    })
    .map((cls) => ({ class: cls, sections: Array.from(map[cls]).sort() }));

  res.json(result);
};

Client Reactive Cascading: In the React client, the custom hook useClassesAndSections binds this data across all ERP screens. When an administrator selects a Class (e.g., 10), the Section dropdown dynamically re-renders to show only sections linked to Class 10 (e.g., Section A, Section B). If the user switches to Class 3, the section automatically cascades and locks to Section C. Manual text input is completely prohibited across ClassFees, Attendance, AttendanceLog, ManageTimetable, SessionalMarks, FinanceControl, and Student Registration.

4.2 Financial Ledger & Settlement Finite State Machine

Tuition billing follows deterministic finite state machine rules:

Settlement Status Mathematical Invariant System Enforcement Policy
PAID paidAmount == totalAmount Balance due is exactly 0. Invoiced status is fully cleared.
PARTIAL 0 < paidAmount < totalAmount Balance due is positive (totalAmount - paidAmount). Student remains on arrears ledger.
PENDING paidAmount == 0 Zero payment recorded. Invoiced total represents 100% outstanding balance.
OVERPAYMENT REJECTED paidAmount > totalAmount Guard Clause: HTTP 400 Bad Request. Prevents accounting distortions. 
// Strict Overpayment Guard in feeController.js
if (numPaid > numTotal) {
  return res.status(400).json({
    message: `Payment amount (${numPaid}) exceeds total invoice dues (${numTotal}). Overpayment rejected.`,
  });
}

4.3 Attendance Registry & Bulk Upsert Pipeline

The daily roll call marks students across three states: present, absent, and late. The controller executes bulk upsert operations using MongoDB's atomic bulkWrite mechanism, ensuring all 40+ student entries in a classroom commit in a single database round-trip without race conditions.

8. Engineering Trade-offs & Architectural Roadmap

Senior developers must acknowledge where trade-offs were made and how they will be resolved as system load scales:

  1. Application-Level vs Database-Level Foreign Key Integrity: MongoDB lacks built-in foreign key cascade deletions. Currently, orphaned attendance or mark records upon student deletion are prevented through controller hooks. A scheduled cron job or MongoDB $jsonSchema collection validators will be introduced to enforce cascade cleanup at the engine layer.
  2. Payment Gateway Automation: The current fee module records manual receipts (Cash, Bank Transfer, Cheque). A webhook reconciliation worker for Razorpay / Stripe is mapped to automatically update paidAmount upon gateway settlement webhooks.
  3. Syllabus Storage Decoupling: Course materials currently store external URL links or base64 data. Migration to AWS S3 / Google Cloud Storage presigned URLs will handle heavy video lectures and textbook PDFs without burdening database BSON limits.
  4. Offline Roll-Call Sync: In campus areas with intermittent Wi-Fi connectivity, faculty roll call will benefit from a progressive web app (PWA) IndexedDB queue that synchronizes bulk attendance packets once network connection is restored.
